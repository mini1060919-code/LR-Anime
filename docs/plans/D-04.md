# D-04｜招募事件與容量 v0.1

日報 C-06 的黎明 checkpoint 是共用提交界線。D-03 於時點取得資格，玩家在名冊明確確認邀請後建立暫存意圖，下一黎明提交時按最新條件重查。若重載丟失暫存意圖，顯示仍可招募並允許再確認。正式工程需決定意圖是否安全持久化。任何提示、語言切換與歷史事件重播均走唯讀。

1. 事件鍵採 `JSON.stringify([run.id, archetypeId])` 作一次性邀請鍵，結果穩定以該鍵關聯。已加入後即使死亡、離隊、重播或切語言，不能再領同角色。同一 run 的歷史槽位回復可能帶回舊收據，正式工程須先定義可驗證的原支線高水位來源，或阻止舊分支執行唯一招募。
2. 驗證來源 run、期望 checkpoint 世代、合法模板、已解鎖旗標、未用模板與身分分配器。達人口容量時拒絕，沿用 `housingCapacity`。成本提案每次食物 5、水 5，扣除後仍須食物 >30 且水 >20。現有 `tryRecruit` 的庫存門檻只是條件，任何扣價是 D 的新提案。
3. 一次處理一份已確認意圖，先保留其床位並扣除資源，再讓既有普通招募依現況取得剩餘床位。沿用既有 survivor ID 分配器及角色 schema，顧問澪不進候選。正式工程需確保指定模板在隨機補角色前建立。以同一持久化提交存入人口、資源、收據、黎明與 C 日報資料。
4. 回傳結構化結果 joined、already-claimed、locked、no-capacity、insufficient-stock、invalid-request 或未提交的 storage/stale 錯誤。容量或成本拒絕可重新確認。失敗維持已提交資料、原 ID 與備份，成功後的遲到通知只回傳舊收據。禁止拆成獨立不可回復的扣款與人口新增。
