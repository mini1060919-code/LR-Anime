## 3. 測試矩陣（全部為規劃，尚未執行）

### 身分、角色與原本模擬

| ID | 案例 | 驗收結果 |
| --- | --- | --- |
| I01 | 同 seed 開新 run、相同居民數字 ID | runId／UID 不同，不讀到舊人物檔案 |
| I02 | 同一 v4 與包在 v5 中的相同 core；JSON 物件 key 排序不同 | canonical hash／姓名生成一致；保留有語義的 core 陣列順序 |
| I03 | generator／內容目錄升版後重讀已保存 v6 | 已保存人物不重抽、不改名，不把人物換成另一原型 |
| I04 | 最高編號居民死亡 → 保存 → 讀取 → 招募 | 保留高水位，新 ID／UID 不重用；死者不在 active records |
| I05 | 生存死亡、建築倒塌死亡、拆除釋放、停用釋放、手動增減與自動指派 | 人口、工作容量、順序、reputation 與原核心規則一致；無幽靈連結 |
| I06 | 固定人物死亡後再次招募 | usedUniqueArchetypeIds 仍保留；不生成同一故事人物的「復活版」 |
| I07 | 原型或可選文案缺失 | 使用姓名快照與通用介紹；保存原 ID，不重抽、不中斷遊戲 |
| I08 | 輸入特殊 Unicode／HTML 字串姓名 | grapheme 長度／控制字元驗證；DOM 僅文字呈現，無 HTML 執行 |
| I09 | 開關人物面板、切換肖像／表情／語言 | 權威居民、資源、工作及 saved bytes 不因呈現操作而變更；尊重原暫停狀態 |

M3-A 的等價測試使用固定 seed、固定 dt 序列與相同命令序列，對照原 M2 authoritative state：居民數量／工作、每項資源、研究、招募、死亡、建築 HP、波次與遊戲結束條件。排除純視覺亂數、面板選取及新人物介紹欄位；不得藉此排除真正模擬差異。

### 存檔、容量與回復

| ID | 案例 | 驗收結果 |
| --- | --- | --- |
| S01 | 合法完整 v4、v5 → v6 → 寫入 → 讀取 → 再寫入 | core 語義與舊還原結果一致、人物資料完整往返；原始 bytes 有永久備份 |
| S02 | v4/v5 選配欄位缺失、資源高於基本上限、工作名冊需重建 | 符合原正規化規則，沒有偷偷減少人口或丟建築／研究；對照 fixture |
| S03 | legacy 無居民欄位或空名冊 | 不在無提示下提交「補人後」的 v6；原檔可匯出，顯示需確認的復原例外 |
| S04 | M3 原生 v6 為明確零人口 | 不呼叫 legacy 補 4 人路徑，不復活居民；維持結束條件 |
| S05 | 壞 JSON、未知 outer/schema/required feature、重複 UID、資料 join 不完整、非有限數值 | 主檔與永久備份不變；可匯出原始檔，不自動開始可覆寫的新檔 |
| S06 | 角色產生、內容載入、hash、實際地圖重建任一步驟失敗 | 沒有部分 v6 或 sidecar 提交；保留原 v4/v5，報告具體步驟 |
| S07 | 備份寫入、主檔替換、驗證讀回、釘選更新分別失敗 | 明確區分失敗／已成功但清理警告；不犧牲永久備份或清空角色資料 |
| S08 | 真實瀏覽器 localStorage 滿額與一般備份 3 份輪替 | 保留原主檔和釘選；錯誤不遮住匯出／復原鈕；釋放測試資料後可重試 |
| S09 | v6 三槽位、跨 run 匯入、從舊槽讀 v4/v5、JSON 往返 | 每次整體替換 core+characters+run；不與目前人物表混用；舊來源先備份 |
| S10 | 舊 M1/M2 開啟 v6 主檔與槽位 | 拒絕未知版本的自動寫入、保留 raw；不得宣稱舊版可繼續玩同一 v6 進度 |
| S11 | 顯式匯出 legacy 降版副本 | 告知不含 M3 人物資料；v6 原檔保留；不以降版資料直接覆寫原 key |
| S12 | 候選 v6 超過 2 MiB；10,000 人的 validator 邊界 | 安全拒絕寫入並保留原檔是預期結果；不能默默截斷或提高上限。正常規模 fixtures 必須成功 |
| S13 | 多分頁改變已選備份／釘選 | 偵測到已變更即停止該次替換；保留單分頁契約，不宣稱 localStorage 多 key transaction 已解決 |

對於過大的合法舊檔，不能以「舊 validator 接受 10,000 人」推論完整 M3 人物記錄也能裝入 2 MiB。若產品要求該規模也可升級，須另設緊湊角色編碼／內容共享設計與壓力測試；不得為通過測試而刪除角色。升級無法完成時，保留來源、只讀預覽及匯出，不自動改用會遺失 M3 欄位的 v5 writer。

### 能力效果專屬關卡（不屬 M3-A 預設）

- 關閉 feature、所有能力 0、缺角色資料時，經濟／傷害結果與原版精確一致。
- 技能聚合按居民 ID 穩定計算；更換陣列排列、讀檔、工作調動不造成非預期差異。
- 無工人設施、停用設施、缺電／缺燃料、非相關職業不能繞過原限制。
- 個別與整體加成上限、研究／建築升級疊加、舍入與 dt 差異皆有案例。
- 不偷偷改敵人 HP、攻速、招募或維生門檻來補償新能力。能力啟用必須獨立平衡報告及人工驗收。

## 4. 效能與美術驗收預算

下列是建議目標，**尚未量測**，不是現況效能承諾：

- 初次進入 3D 遊戲不預載全圖與全部表情；人物面板失敗不拖垮 GLB boot。
- 先提供 50–100 人可操作名冊；大量資料採分頁／虛擬列表，不建立 10,000 個按鈕或每幀重建所有角色 DOM。
- 完整立繪採有界快取，例如同時保留 2 張 decoded 全圖；1024×1536 RGBA 單張約 6 MiB，2 張約 12 MiB，**不包含瀏覽器／GPU／3D 貼圖開銷**。不可把 350 KiB 網路檔案大小當成解碼記憶體。
- 在參考桌面與一個行動裝置記錄面板開啟、快速切換、快取回收與記憶體；軟體 WebGL CI 只檢查正確性，不拿它冒充硬體效能報告。
- 美術驗收：三種表情確為同一人、裁切不截斷重要部位、縮圖可辨識、透明邊緣無白邊、深淺背景均可讀、角色身分不靠顏色單獨辨識。

## 5. M3-A 完成定義

以下全部成立才建議接受第一批 M3 實作：

1. 設計、schema、身分、內容目錄與授權流程已有測試對應，無 runtime 依賴未知來源素材。
2. 所有既有單元／瀏覽器測試通過；新增 identity、migration、quota、人物生命週期與 fallback 案例通過。原 M2 的 466／6 僅作歷史起點，未來新增／調整後報告實際數量與 skipped／failed。
3. `npm run build` 成功；不透過停用斷言、改 checksum／TLS 或刪除舊檔取得綠燈。
4. v4/v5 合法正常檔升級成功、永久原檔可下載；歧義、損壞、未知或容量不足檔案安全停止。
5. core 與人物整體往返，slot／import 不串 run；姓名、UID、素材 revision 不因重讀或語言改變而漂移。
6. 舊版不能讀 v6 的限制及明確降版副本已說明，並有實際回復演練。
7. 模擬差異為零（M3-A）；圖像、面板與角色設定不能改原工作、經濟、死亡、招募、殭屍夜襲或 Three.js 地圖。
8. 提供檔案清單、測試日誌、視覺截圖、素材來源摘要、已知限制及回復方式。人工審查後才決定是否合併；發布仍須另外授權。

## 6. 回復與例外策略

- M3 v6 成功升級前失敗：保留原 v4/v5，不提交半套資料；可下載來源並重試。
- 已有 v6 但要回舊版：先匯出並保留完整 v6，再由使用者選擇不含人物資料的 legacy 副本；不在背景自動降版。
- 素材／目錄出錯：關閉 portrait resolver、退回剪影；不刪人物、不關閉核心存檔。
- 角色能力出錯：僅 M3-C 有該 feature；保留原角色資料，先停用效果並記錄規則版本，不默默清零能力。
- 程式回復採後續實作 commit 的 `git revert`，不重設 main、不刪 localStorage、不替換使用者未備份的檔案。
